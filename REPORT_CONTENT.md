### Deviations from the PRD / proposal (all are marked `# NOTE:` in the code)
1. **Coverage readout.** PRD: run `-runs=0` and parse `cov:`/`ft:`. Done instead: libFuzzer merge mode per input (`<bin> -merge=1 -save_coverage_summary=<f>` or `-merge_control_file=<f>`), which writes the exact feature IDs of that single input. Reason: each execution is a fresh process, so `ft:` counts only that input and "ft rose" would reward bigger inputs rather than new code. For `hello`, merge mode matches `-runs=0` `ft:` on 5 of 6 cases and reports 508 vs `ft:` 455 on 10304 (comment in `arvo_env.py`; not re-measured here). Two libFuzzer generations are present: `summary` mode (12950, 3848, 10304, 3522) and `control` mode (13222, 16091).
2. **"New coverage".** Defined as feature IDs never seen earlier in the same episode (union kept in Python), not "cumulative ft rose". (source: `arvo_env.py`)
3. **Baseline seed runs.** The initial seeds are executed once at `reset()` to set baseline coverage; these executions do not count toward T (`seed_executions` column).
4. **Seed for each step.** Following the proposal (Algorithm 1, Eq. 1), the seed is drawn uniformly before the agent acts and the state's size bucket is that seed's size. The same uniform draw is used for all three agents.
5. **Setting A seeds.** 12950 and 10304: three hand-made valid inputs each (proposal P4). 13222, 3522, 16091: first 10 of the OSS-Fuzz corpus zip after a size-spread ordering; 3848: 5 seeds. The cap of 10 seeds and the 8192-byte size limit are our choices, not in the proposal. 16091 seeds are prefixed with the two harness option bytes `00 01`. All seeds were checked not to crash the `-vul` build.

7. **Crash verification.** In-run (`ArvoEnv._verify`): the saved input is re-run on the `-vul` binary and on a copy of the `-fix` binary extracted from the `-fix` image (`extract_fix_binary.sh`, run inside the `-vul` container; the script first checks that the system libraries of both images are identical). A crash counts only if `-vul` reproduces it and the `-fix` binary exits 0 with no ASan report. After the run, `verify_on_fix_image.py` re-ran every saved crash through the real `docker run n132/arvo:<id>-vul` and `...-fix` images: 35 crash files checked on real images; 35 verified (vul ASan crash, fix exit 0, no ASan) (source: `results/full_T5000/fix_image_check.csv`)
8. **Episode end.** A run ends at the first crash (verified or not) or after T executions. In the 180 runs every found crash was verified (35 found, 35 verified). (source: `results/full_T5000/*/runs.csv`)
9. **Q-learning terminal step.** The update always bootstraps from `max Q[s',:]`, including on the final (crash) step; the shared agent interface has no `done` flag. (source: `agents/qlearning_agent.py`)
10. **Crash deduplication.** The top-3-frame rule is applied only in the analysis (`metrics.py`, `distinct_crashes.csv`), after the runs, by exact string match of the three frame strings. It is not used during runs (each run stops at its first crash anyway).
11. **Parallel execution.** 24 containers ran at once (one per case x setting x seed group {0,1,2} / {3,4}), which lowers per-run speed but does not change results. Python analysis ran on the host.
12. **Superseded run.** An earlier full run at T=2000 with a different state definition and different seeds for 12950/10304 is archived in `results/full_T2000_old/`. It is not used and not reported.

## Introduction

[Written for the report; every claim below is tied to what the code does.]

Fuzzing feeds a program many altered inputs and watches for crashes. A mutation-based fuzzer must repeatedly choose which edit to apply to a seed. Learning-based schedulers for this choice have been reported to help, but the crashes they report are rarely checked against a developer's fix, so it is hard to tell real bugs from noise. ARVO supplies real, already-fixed memory-safety bugs as pairs of Docker images (`-vul`, `-fix`), which allows every crash to be verified.

This project formulates operator selection as a Markov decision process whose environment is one ARVO vulnerable build, and compares three schedulers under an identical seed scheduler and budget: tabular Q-learning, a UCB1 bandit and uniform random choice. What was built:
- `ArvoEnv` (`arvo_env.py`): drives one target inside its `-vul` container, reads per-input coverage and crashes, and verifies crashes against the fixed build.
- Eight mutation operators (`mutators.py`) and three agents (`agents/`).
- A runner (`run_experiment.py`) for two settings: from seeds (A) and from a perturbed PoC (B).
- A metrics module (`metrics.py`) producing tables, Mann-Whitney U and A12 tests and plots.

Research questions: RQ1 coverage of Q-learning vs Random; RQ2 executions to a verified crash for Q-learning vs Random and UCB1; RQ3 which operators the learned policy prefers per input format.

## Proposed Model / Methodology

**Execution of one input.** `<fuzz binary> -merge=1 -artifact_prefix=<scratch>/ [-save_coverage_summary=<file> | -merge_control_file=<file>] <empty dir> <dir holding the one input>` with the ASan options copied from the image's `arvo` script (`config.py`). The feature IDs written to the file are the coverage of that input. A run that exceeds 25 s is treated as no crash and no coverage. A crashing input contributes no features. (source: `arvo_env.py`, `config.py`)

**State.** `s = (previous_action, got_new_coverage, size_bucket)`. `previous_action` is 0-7 or 8 for "none yet"; `got_new_coverage` is 1 if the previous step found at least one never-seen feature; `size_bucket` is of the seed selected for this step: S (< 64 bytes), M (64-1024), L (> 1024). 9 x 2 x 3 = 54 states, indexed `(prev*2 + new)*3 + size`. (source: `arvo_env.py`)

**Actions (`mutators.py`).** All operators return non-empty bytes (an empty input is first replaced by one random byte).
1. `bit_flip`: flip one random bit.
2. `byte_flip`: XOR one random byte with 0xFF.
3. `random_byte`: replace one byte with a random value different from the current one.
4. `insert_bytes`: insert 1-4 random bytes at a random position.
5. `delete_bytes`: delete 1-4 bytes at a random position (never the last remaining byte).
6. `interesting_value`: overwrite 1, 2 or 4 bytes with a value from {0, 1, 0x7F, 0x80, 0xFF, 0x7FFF, 0xFFFF, 0x7FFFFFFF, 0xFFFFFFFF} that fits the width, in random byte order.
7. `duplicate_chunk`: copy a 1-32 byte chunk and insert it at a random position.
8. `splice`: keep a prefix (at least 1 byte) of the seed and append a suffix (at least 1 byte) of another pool seed; with a one-seed pool it splices the seed with itself.

**Transition.** The seed for the step is drawn uniformly from the pool (before the agent chooses); the chosen operator produces a child; the target runs on the child; if the child has at least one never-seen feature it joins the pool; the next seed is then drawn from the updated pool. Seed selection is identical for all three agents.

**Reward.** `r = min(new_features, 10)/10 + 10*crashed`, where `new_features` counts feature IDs not yet seen in the episode. If coverage were unavailable the reward would be `10*crashed`; this fallback was never triggered.

**Episode.** Ends at the first crash or after T = 5000 executions. Baseline executions of the initial seeds are not counted.

**Agents.**
- Random: uniform over the 8 operators; `update` does nothing.
- UCB1: stateless; tries each operator once, then picks `argmax(mean_reward[a] + sqrt(2) * sqrt(ln(t)/n[a]))`, t = pulls so far.
- Q-learning: `Q[s,a] += 0.1 * (r + 0.9 * max Q[s',:] - Q[s,a])`; epsilon-greedy with `epsilon = max(0.05, 1 - t/(0.2 T))`; ties broken uniformly at random.
- Reproducibility: the environment and agent RNGs are seeded with the run seed (0-4); the Setting B perturbation uses seed 1000 + run seed.

**Experiment design.** 3 agents x 6 cases x 2 settings x 5 seeds = 180 runs. Setting A starts from the seed set; Setting B starts from the perturbed PoC.

**Metrics (`metrics.py`).**
- Success rate: verified-crash runs / 5.
- Executions to first verified crash: median over successful runs only (summary table); in the Mann-Whitney test, runs without a verified crash are ranked as T+1 = 5001 and cells where all values are equal are not tested.
- Final coverage: number of distinct features seen in the episode, mean ± std (sample std).
- Coverage AUC: mean of the coverage curve over executions 1..T, where a run that stopped at a crash is extended flat at its last value.
- Operator usage: share of mutations per operator, pooled over seeds.
- Tests: `scipy.stats.mannwhitneyu` two-sided, alpha 0.05, on final coverage, coverage AUC and executions to crash; A12 reported as the probability that Q-learning is better (higher coverage; fewer executions). Thresholds on |A12 - 0.5|: negligible < 0.06, small < 0.14, medium < 0.21, otherwise large.

## Discussion

**RQ1: does Q-learning reach higher coverage than Random?** In 11 of 12 case-setting cells Q-learning's mean coverage AUC is above Random's (the exception is 16091 B, 47.4 vs 47.5), and in 10 of 12 above UCB1's (exceptions 13222 A and 16091 B) (computed from the AUC table). The gaps are mostly small compared with the run-to-run spread: only 3522 A is significant against Random (AUC p = 0.0079, A12 = 1.0; final coverage p = 0.0212, A12 = 0.96) and against UCB1 only final coverage on 3522 A (p = 0.0459, A12 = 0.90); no AUC comparison against UCB1 is significant. The next-closest result against Random is 12950 A (AUC 4611.9 ± 785.3 vs 3872.3 ± 1179.0; p = 0.0952, A12 = 0.84). Overall, 72 comparisons, 55 testable, 3 with p<0.05 (the remaining comparisons had identical values in both groups); 3 of 55 testable tests is about the 2.75 expected by chance at alpha 0.05 with no correction. The evidence for H1 is therefore weak: a consistent but small and mostly non-significant direction in favour of Q-learning, with one significant case.

**RQ2: fewer executions to a verified crash (Setting B)?** Not supported. Crashes exist in Setting B only for 12950 and 13222.
- 12950 B: success Random 5/5, UCB1 2/5, Q-learning 3/5; medians 334, 165.5, 449. Q-learning vs Random p = 0.402 (A12 0.32), vs UCB1 p = 1.0 (A12 0.52).
- 13222 B: all agents 5/5; medians Random 90, UCB1 161, Q-learning 1405. Q-learning vs Random p = 0.4206 (A12 0.32), vs UCB1 p = 0.3095 (A12 0.28).
Q-learning was slower or less reliable than Random in both, and no difference is significant. In Setting A, 12950 yielded crashes for all three agents (Random 2/5, UCB1 4/5, Q-learning 3/5; no significant difference) and 13222 only once (UCB1). H2 is not supported; with n = 5 and two usable cases this is also not strong evidence against Q-learning.

**RQ3: operator preferences.** Random is flat at about 12.5% by construction (12.25-12.99% in the table), as a sanity check. Q-learning concentrates on a few operators, differently per case:
- `splice` is its top operator on 3522 (33.76%), 10304 (22.60%), 13222 (20.70%) and 3848 (17.96%).
- `duplicate_chunk` on 12950 (32.17%); `insert_bytes` on 16091 (17.56%).
- It under-uses `interesting_value` on 12950 (4.17%), `random_byte` on 3522 (5.45%) and 12950 (6.38%), and the bit/byte flips on 13222 (8.16%, 8.02%).
UCB1 shows a weaker version of the same tilt (e.g. `splice` 25.36% on 3522, `duplicate_chunk` 22.70% on 12950). On 16091 coverage stays near 48 features for all agents in Setting B, and Q-learning's usage there is closest to uniform apart from `insert_bytes` (17.56%). For H3 (text vs binary): the text targets favour `duplicate_chunk` (12950) and `splice` (10304) and the binary targets `splice` (3848) and `insert_bytes` (16091); there is no clean text/binary split and no formal test was run, so H3 is only descriptively explored. Operator preference here reflects what produces new coverage (the reward is mostly coverage), not what finds the bug.

**Negative and inconclusive results (stated plainly).** Q-learning did not find crashes faster than the baselines; four of six cases produced no crash at T = 5000; most coverage differences are within one standard deviation.

**Threats to validity.**
- Few cases: only 2 of 6 cases yield crashes, so crash-based conclusions rest on pcre2 and file.
- Small samples: n = 5 per group; the smallest possible two-sided p with 5 vs 5 is about 0.008, and no multiple-comparison correction was applied.
- Setting B is dominated by the tiny PoCs of 12950 and 13222 (4 and 6 bytes, one byte changed), so it measures local mutation around a near-crash input rather than discovery; early crashes also confound coverage metrics.
- Budget: T = 5000 executions; coverage curves are visibly still rising at 5000 executions in most Setting A panels (`coverage_A.png`).
- Coverage definition: merge-mode feature IDs, not `ft:` from `-runs=0`; 10304's count differs between the two readouts.
- Seed sets were partly hand-made (12950, 10304) and capped (10 seeds, 8 KiB); results depend on them.
- Crash grouping is exact string matching on frames, so the same bug can split into several groups.
- Run-to-run variance is large in Setting B (e.g. the final-coverage std is about half the mean for 12950 B in all three agents; see the final-coverage table).
- Uncommitted code state produced the results (see manifest).

## Conclusion

**Findings.** On six ARVO bugs, with all crashes verified against the developer's fix (35 of 35 on the real images), tabular Q-learning did not clearly outperform uniform random or UCB1. Q-learning's coverage was nominally higher in most cells but significant in only one (3522, Setting A); it was not faster to a verified crash. The learned policies favour byte-rearranging operators (`splice`, `duplicate_chunk`, `insert_bytes`) over bit-level ones, with case-specific differences.

**Contributions.** (1) An ARVO-based fuzzing MDP environment with a verified-crash oracle (`arvo_env.py`) for six targets; (2) a controlled comparison of three operator schedulers with identical seed scheduling and budget over 180 runs; (3) an analysis pipeline (tables, Mann-Whitney U, A12, plots) and a post-hoc re-verification of every crash on the real `-vul`/`-fix` images.

**Limitations.** Two crash-yielding cases; 5 runs per cell; T = 5000; merge-mode coverage; partly hand-made seeds; single machine; no multiple-comparison correction; the results come from an uncommitted working tree.

**Future work (tied to what was done).** More cases that crash within budget (the backups 4088, 11752, 9847 are untested), more repeats, longer budgets, a coverage readout via `-runs=0` to compare with merge mode, and letting the agent also choose seeds.
